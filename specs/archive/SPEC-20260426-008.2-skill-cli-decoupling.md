# SPEC-008.2 — Skill bin/ decoupling from vanilla-Pi extension imports

## 1. Goal

- Eliminate the three TypeScript imports of `../../../extensions/...` paths
  from ported `.omp/skills/*/bin/*.ts` and `.omp/skills/*/test/*.ts`. Today
  these resolve correctly under `.pi/` (where `extensions/` exists), but
  resolve to a non-existent `.omp/extensions/` directory under Oh My Pi.
  Skills that hit this code path (`memory`, `docs`) currently fail at
  module-load time when invoked under `omp` — turning SPEC-008 acceptance
  criterion **A6** red.
- Honor the CLAUDE.md "Skill boundaries" rule literally:
  *"Extensions for in-process state ... Skills for external CLI wrappers
  ... Skills NEVER write to in-process state."* Skills must not
  TS-import code from the project's extension surface; what they need
  must be carried with them or fetched at the filesystem boundary.
- Restore A6 to green without altering any skill behavior, without
  touching `.pi/extensions/`, and without introducing a new shared
  TypeScript module that re-couples the skill bin scripts to extension
  internals.
- Keep the change small enough that test-writer + implementer can land
  it in one round.

## 2. Scope

In scope:

- Modify the three files that carry the offending imports:
  - `.omp/skills/memory/bin/memory.ts` (lines 19–21).
  - `.omp/skills/memory/test/memory.test.ts` (line 16).
  - `.omp/skills/docs/bin/docs.ts` (line 20).
- Inline the tiny surface they consume into each skill's `bin/` directory
  (per §3.1 decision below): a per-skill local module
  `.omp/skills/memory/bin/_specsafe-state.ts` and
  `.omp/skills/docs/bin/_specsafe-state.ts` containing copies of
  `statePathFor`, `readStateFileOrNull`, and the four exported types
  (`StateFile`, `CostCounter`, `CurrentSlice`, `HistoryEntry`). The
  `memory` skill additionally inlines `CONCLUSION_WRITERS` (a one-liner
  `ReadonlySet<string>`).
- Update the skill bin/test imports to reference the new local module
  instead of the cross-tree extension path.
- Add canonical-shape pin tests under `.omp/test/`:
  - `.omp/test/specsafe.test.ts` — pins `statePathFor`,
    `readStateFileOrNull`, and the `StateFile` shape against the
    extension's exports so that drift between
    `.pi/extensions/specsafe-session/index.ts` and the inlined skill
    copies is caught at the test boundary.
  - `.omp/test/honcho.test.ts` — extend (don't replace) the existing
    file with a `[unit] CONCLUSION_WRITERS pin` block that asserts the
    set equals `{validator, reviewer, steward}` so that any drift
    against either the canonical extension constant or the inlined
    skill copies is caught.
- Update `.omp/skills/memory/SKILL.md` and `.omp/skills/docs/SKILL.md`
  with a one-line note that the skills are self-contained: no
  extension-surface dependency.
- Verify by inspection that no other ported skill (`push`, `linear`,
  `github`, `latest-docs`) imports from `../../../extensions/`. Per
  the audit in §3.4 below the answer is "no", but the implementer
  re-runs the grep as the first step and surfaces if anything new has
  appeared.

Not in scope:

- Modifying `.pi/extensions/specsafe-session/index.ts`,
  `.pi/extensions/honcho/index.ts`, or any other vanilla-Pi extension.
  Vanilla Pi remains the authority for the in-process surface; the
  inlined skill copies are downstream consumers, not upstream
  rewrites.
- Creating a new shared `.omp/lib/` directory or any cross-skill helper
  package. The §3.1 decision rejects this explicitly.
- Spawning subprocess shell-outs from skill bin scripts to a CLI
  wrapper. The §3.1 decision rejects this explicitly.
- Refactoring the skill `bin/` test harnesses, dispatch shapes, or
  golden-path semantics — the slice is import-surgery only.
- Touching audit-log paths inside skill bin scripts
  (`.pi/.push-log.jsonl`, `.pi/.linear-log.jsonl`, etc.) — they are
  repo-relative not runtime-relative, intentionally coexist between
  `pi` and `omp` invocations, and SPEC-008 §5b.3 defers their
  decommission to slice-009.
- Restructuring skill directory layout, test placement, or SKILL.md
  schemas.
- Any change to identity propagation, `as_peer`, or Honcho tool
  schemas — that's slice-008.1's contract.

## 3. Implementation constraints

### 3.1 Decoupling architecture — DECIDED: inline-copy (option c)

The three handoff-floated options were evaluated against the actual
surface consumed and the load-bearing CLAUDE.md rule.

**Surface consumed by skills today** (verified by reading
`.omp/skills/memory/bin/memory.ts:19–21`,
`.omp/skills/memory/test/memory.test.ts:16`, and
`.omp/skills/docs/bin/docs.ts:20`):

- `statePathFor(cwd: string): string` —
  `.pi/extensions/specsafe-session/index.ts:73–75`. Three lines:
  `path.join(cwd, ".pi", ".honcho-state.json")`.
- `readStateFileOrNull(filePath: string): StateFile | null` —
  `.pi/extensions/specsafe-session/index.ts:77–95`. ~18 lines: existence
  check, JSON parse, structural sanity check, corrupt-file quarantine
  rename, return null on failure. No external deps beyond `node:fs`.
- `CONCLUSION_WRITERS: ReadonlySet<string>` —
  `.pi/extensions/honcho/index.ts:23–27`. One literal:
  `new Set(["validator", "reviewer", "steward"])`.
- Types `StateFile`, `CostCounter`, `CurrentSlice`, `HistoryEntry` —
  `.pi/extensions/specsafe-session/index.ts:25–59`. Pure structural type
  declarations, no implementation surface.

Total programmatic surface: ~24 lines of code plus four type
declarations. No external deps.

**Option (a) — CLI shell-out via `.omp/lib/` runtime-neutral scripts.**
The skill bin scripts would `Bun.spawnSync(["bun", "run",
".omp/lib/specsafe-state.ts", "read-state", cwd])` and parse JSON back.
- *Match against CLAUDE.md.* Honors "Skills for external CLI wrappers"
  literally — the skill becomes a wrapper around a separate CLI surface.
- *Cost.* Adds ~50–100ms of subprocess + JSON parse overhead per skill
  invocation (Bun cold start). The `memory status` and `docs list`
  commands are interactive operator surface; the latency budget is
  tight enough that adding a subprocess hop for every state read is
  user-visible. JSON marshaling at the boundary loses the Type-Box-y
  shape contract that `StateFile` already encodes.
- *Surface inflation.* Creates a new top-level `.omp/lib/` directory,
  a new bun-runnable CLI binary, a documented wire format
  (`read-state` subcommand schema), test surface for that wire format,
  and a third place in the repo where SpecSafe state is read (after
  the canonical extension and the skill bin scripts). Three places
  is worse than two.
- *Verdict.* Over-engineered for a 24-line surface. The argument for
  CLI shell-out is strongest when the underlying surface is
  process-bound (long-running, holds resources, talks to network) —
  none of which applies to two pure helpers and a literal Set.

**Option (b) — Shared TS module at `.omp/lib/specsafe-state.ts`
imported by both hooks AND skills.** Same physical file, imported not
spawned.
- *Match against CLAUDE.md.* Reads the rule the other way: "Extensions
  for in-process state. ... Skills NEVER write to in-process state."
  A shared `.omp/lib/` module that *is* the in-process state surface,
  imported by skills, looks structurally identical to skills importing
  extension code — the same coupling the rule was designed to forbid.
  The fact that the file lives at `.omp/lib/` rather than
  `.omp/extensions/` is a labeling distinction, not a structural one.
- *Cost.* Negligible; type-safe; fastest of the three.
- *Surface inflation.* One new file, one new module, but the *coupling
  graph* now connects skills back to a shared in-process module. The
  next refactor that wants to split the skills out into a separate
  package will hit the same import problem the original
  `../../../extensions/...` import hit — just with a different path
  prefix.
- *Verdict.* Solves the symptom without honoring the principle. If we
  ever add a third surface (say, a future MCP exporter that wants to
  read SpecSafe state), the `.omp/lib/` module starts accreting
  cross-cutting helpers and becomes the in-process extension surface
  by another name.

**Option (c) — Inline-copy the surface into each skill bin/ script.**
A per-skill local module (e.g.
`.omp/skills/memory/bin/_specsafe-state.ts`) carries verbatim copies
of `statePathFor`, `readStateFileOrNull`, the four types, and (for
`memory`) `CONCLUSION_WRITERS`. The bin script imports from `./
_specsafe-state.ts`; no cross-tree dependency.
- *Match against CLAUDE.md.* Honors "Skills NEVER write to in-process
  state" literally: each skill is now self-contained at the
  filesystem boundary. The skill carries everything it needs in its
  own directory; nothing about the skill's correctness depends on
  the extension's continued existence or shape.
- *Cost.* Two new ~25-line files (one per affected skill, since
  `docs` doesn't need `CONCLUSION_WRITERS`). Zero subprocess
  overhead. Type-safe.
- *Drift risk.* The handoff and Luci's prior both raise drift as the
  failure mode: "what if `statePathFor` changes in the canonical
  extension and the inlined copies don't?" This is a real concern.
  Mitigation, per §3.3 below: pin tests under `.omp/test/` that
  cross-check the canonical extension exports against the literal
  shapes the inlined copies must produce. If the canonical extension
  ever changes its `statePathFor` to return a different path, the
  pin test breaks; the implementer either updates the inlined copies
  to match or surfaces the divergence. Drift risk drops from "silent"
  to "noisy CI failure."
- *Verdict.* SELECTED. Smallest change, most-honored principle, lowest
  ongoing coupling, and the drift concern is solved with ~30 lines of
  test that already belong in `.omp/test/` for unrelated reasons
  (canonical-shape pinning is a generally healthy pattern when the
  same constant or function lives in two places).

**Why this decision coheres with slice-008.1.** Slice-008.1 chose
"accept model-trust degradation explicitly and document it" over
chasing a partial mitigation that would add load-bearing fragility
(the sessionManager-substring-match approach). The same discipline
applies here: option (b) is a *labeling* mitigation that makes the
import path look cleaner without removing the underlying coupling.
Option (c) takes the explicit trade-off — inline-copy with pin tests —
and makes the cost visible and bounded.

**Why this decision coheres with the broader pi-seshat philosophy.**
The repo CLAUDE.md "Skill boundaries" section is the load-bearing
text: *"Skills for external CLI wrappers (gh, linear SDK, git push,
BMad-doc edits, latest-docs fetchers). Skills NEVER write to
in-process state."* The skill bin scripts in question (`memory`,
`docs`) are predominantly external-CLI wrappers already (`docs`
shells out to `git`; `memory` shells out to the Honcho SDK). The
small amount of in-process state they read (the SpecSafe state file)
is read at the *filesystem boundary*, not at the in-process surface.
Inlining the tiny filesystem-reader keeps the skill at that boundary
where it already mostly lives.

### 3.2 Inlined module shape — DECIDED

Each affected skill carries a single new file
`<skill>/bin/_specsafe-state.ts` (the leading underscore signals
"local helper, not part of the skill's public dispatch surface"). The
file:

- Has a top-of-file docstring stating: "Inlined from
  `.pi/extensions/specsafe-session/index.ts:25–95` and (for memory)
  `.pi/extensions/honcho/index.ts:23–27` per SPEC-008.2 §3.1. If you
  modify the canonical extension, run `bun test .omp/test/specsafe.test.ts`
  and `bun test .omp/test/honcho.test.ts` and update this file in lock-step
  if the pin tests fail. See SPEC-008.2 §3.3 for the drift-detection
  contract."
- Exports `statePathFor`, `readStateFileOrNull`, and the four types
  (`StateFile`, `CostCounter`, `CurrentSlice`, `HistoryEntry`) with
  byte-identical implementations to the canonical extension at the
  cited line range. Only the import lines (the canonical file imports
  `node:fs` and `node:path`; the inlined file imports the same; no
  Honcho or pi-coding-agent imports are needed for the surface in
  question, so none are carried over).
- For `memory` only: additionally exports
  `CONCLUSION_WRITERS: ReadonlySet<string> = new Set(["validator",
  "reviewer", "steward"])` with the same comment-link pointing to
  `.pi/extensions/honcho/index.ts:23–27`.

The implementer does NOT export `freshCostCounter`, `emptyState`,
`writeStateFile`, `buildSpecsafeSessionTools`, the Pi extension
default export, or any other surface from the canonical extension
that the skills don't actually consume. Inline-copy is strictly
"the surface the skill imports today, no more."

### 3.3 Drift-detection pin tests — DECIDED

Two new test files (or extensions of existing test files) under
`.omp/test/`:

- `.omp/test/specsafe.test.ts` (new file). Imports both the canonical
  extension (`.pi/extensions/specsafe-session/index.ts` — the existing
  file, untouched) AND the inlined skill copies
  (`.omp/skills/memory/bin/_specsafe-state.ts`,
  `.omp/skills/docs/bin/_specsafe-state.ts`). Asserts:
  1. `statePathFor` from canonical and from each inlined copy returns
     the same string for the same `cwd` input. Three test cases:
     a typical absolute path, a path containing spaces, a relative
     path. (Three runs × two inlined copies = six assertions per
     case; all must agree.)
  2. `readStateFileOrNull` from canonical and from each inlined copy
     returns structurally-equal results for: a non-existent path
     (both return `null`), a well-formed state file (both return the
     same parsed `StateFile`), a malformed JSON file (both return
     `null` AND quarantine to a `.corrupt-*` rename — assert the
     rename happened in both cases).
  3. The `StateFile` type's structural fields (`currentSlice`,
     `history`) are present on both — verified by writing a fixture
     state, reading via canonical, reading via inlined, and asserting
     `JSON.stringify`-equality.
- `.omp/test/honcho.test.ts` (extend existing file — see slice-008.1
  for the file's current shape). Add one new `describe` block:
  `[unit] CONCLUSION_WRITERS pin` — imports `CONCLUSION_WRITERS` from
  canonical (`.pi/extensions/honcho/index.ts`) AND from the inlined
  copy in `.omp/skills/memory/bin/_specsafe-state.ts`. Asserts the
  two sets contain the same elements (`["validator", "reviewer",
  "steward"]`) and have the same size (3).

These tests are the slice's load-bearing safety net. If a future
edit to the canonical extension changes `statePathFor` to a different
path, or alters `readStateFileOrNull`'s quarantine semantics, or
adds/removes a `CONCLUSION_WRITERS` member, the pin test breaks
loudly in CI. The implementer of that future change either updates
the inlined copies in lock-step or surfaces the divergence to Luci
for an explicit re-decision.

### 3.5 Test-file imports — DECIDED

`.omp/skills/memory/test/memory.test.ts:16` is a `import type {
StateFile }` — pure type import, no runtime cost. After the
refactor, this import points at the same inlined module the bin
script uses (`../bin/_specsafe-state.ts`). This keeps the test
asserting against the same `StateFile` shape the bin script
operates against; if the bin's inlined `StateFile` ever drifts
from canonical, the pin test in `.omp/test/specsafe.test.ts`
catches it independently of the per-skill test suite.

The existing memory test suite at lines 33–113 constructs literal
`StateFile` fixtures. Those fixtures are byte-compatible with the
inlined type shape (which is byte-compatible with canonical, by
construction); no fixture rewriting is needed.

### 3.6 SKILL.md updates — DECIDED

`.omp/skills/memory/SKILL.md` and `.omp/skills/docs/SKILL.md` each
get one new line in the "implementation notes" or equivalent section:
"This skill carries inline copies of the `statePathFor` /
`readStateFileOrNull` helpers from `.pi/extensions/specsafe-session`
(memory also inlines `CONCLUSION_WRITERS` from
`.pi/extensions/honcho`) so that it runs identically under `pi` and
`omp`. Pin tests under `.omp/test/specsafe.test.ts` and
`.omp/test/honcho.test.ts` enforce shape parity with the canonical

If the skill's SKILL.md doesn't currently have an
"implementation notes" section, the line goes at the end under a new
`## Implementation notes` heading. SKILL.md format is identical
between vanilla Pi and Oh My Pi (per SPEC-008 §2 scope), so this
edit is portable.

### 3.7 Backwards compatibility

- `.pi/extensions/specsafe-session/index.ts` and
  `.pi/extensions/honcho/index.ts` are **not modified**. Vanilla Pi
  invocations continue to work unchanged.
- `.pi/skills/memory/bin/memory.ts`, `.pi/skills/docs/bin/docs.ts`,
  `.pi/skills/memory/test/memory.test.ts` are **not modified**. The
  vanilla skills continue to import from the relative-path canonical
  extensions, which resolve correctly under `.pi/`.
- The Oh My Pi ports under `.omp/skills/` were earlier slice-008.0
  copies of the vanilla skills with import paths kept identical (the
  bug). After this slice, the omp ports diverge from the vanilla
  skills only on the import lines themselves; dispatch logic, test
  fixtures, and golden-path semantics remain identical.
- A future slice that decommissions `.pi/` (slice-009 candidate) would
  need to either move the canonical extension surface elsewhere OR
  delete the pin tests in `.omp/test/specsafe.test.ts` /
  `.omp/test/honcho.test.ts` since they'd no longer have a canonical
  to pin against. The pin tests' import path documents this
  dependency explicitly so the future decommissioner can't miss it.

## 5. Open questions / risks

### Resolved (decisions made in this spec; do not re-litigate during implementation)

- **§3.1 — Decoupling architecture.** Option (c) inline-copy. Options
  (a) and (b) rejected with primary-source reasoning; see §3.1.
- **§3.2 — Inlined module shape.** Per-skill local
  `_specsafe-state.ts` with byte-identical implementations from the
  canonical extension at the cited line ranges, plus a docstring
  pointing at SPEC-008.2 §3.3 for the drift-detection contract. No
  surface beyond what the skill consumes.
- **§3.3 — Drift detection.** Pin tests under `.omp/test/` cross-check
  canonical vs inlined for `statePathFor`, `readStateFileOrNull`,
  and `CONCLUSION_WRITERS`. Failure is loud CI break, not silent
  drift.
- **§3.4 — Other skill audit.** Verified empty for `push`, `linear`,
  `github`, `latest-docs`. Implementer re-runs the grep as step 0
  and surfaces any new occurrences.
- **§3.5 — Test-file imports.** Memory test imports the inlined
  module path; type-only import; no fixture rewrites needed.
- **§3.6 — SKILL.md updates.** One implementation-note line per
  affected skill, naming SPEC-008.2 and the pin-test files.
- **Naming convention for the inlined module.** `_specsafe-state.ts`
  with leading underscore (matches the "local helper, not public
  surface" convention used elsewhere in the codebase). Not
  `lib.ts`, not `state.ts`, not `helpers.ts` — those would invite
  later accretion of unrelated helpers into the same file.

### Remaining for implementer to surface during execution

- **New extension imports between spec and implementation.** If any
  `.omp/skills/*/bin/*.ts` or `.omp/skills/*/test/*.ts` has gained
  a new `../../../extensions/` import between spec authoring and
  implementation (slice-008.1 might have added one if its persona
  changes also touched skill code, though §3.4 of slice-008.1 says
  it does not), surface the diff before applying. Add the new
  import to the inline-copy work; do not silently leave it.
- **Pin test scope expansion.** If the implementer discovers during
  implementation that the canonical extension's
  `readStateFileOrNull` has subtle behavior the inlined copy doesn't
  reproduce (e.g., the corrupt-file quarantine rename uses a
  timestamp that's tricky to match), the pin test for that case
  needs to be more structural ("rename happened" rather than "rename
  to exact path X"). Surface if more than trivial reshaping of the
  pin test is needed.
- **`.pi/` deletion sequencing.** SPEC-008 §5b.3 notes that
  decommission of `.pi/` happens in slice-009. The pin tests in this
  slice depend on `.pi/extensions/...` continuing to exist. The
  slice-009 author needs to know to either move the canonical
  somewhere stable, or delete the pin tests as part of decommission,
  or both. This dependency is documented inside the pin test files
  themselves (file-header comment) and called out here so it isn't
  lost.

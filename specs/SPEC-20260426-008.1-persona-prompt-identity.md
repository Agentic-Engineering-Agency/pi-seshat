# SPEC-008.1 — Per-Ghola identity propagation under Oh My Pi

## 1. Goal

- Restore the per-Ghola identity invariant that vanilla Pi enforced via
  `child_process.spawn` per-call env injection (`HONCHO_PEER_ID` per dispatched
  agent), but inside Oh My Pi's in-process `task` runtime where no such
  per-spawn env-injection seam exists (see `.omp/hooks/PORT-NOTES.md:44–55`
  and primary-source confirmation in §3.1 below).
- Make `honcho_conclude`'s validator/reviewer/steward allowlist meaningful
  again under `omp`. Today, allowlist enforcement is bypassed-by-accident
  whenever the parent orchestrator's `HONCHO_PEER_ID` env happens to be a
  conclusion-writer (or vacuous in test harnesses); see
  `.omp/tools/honcho/index.ts:312–322`.
- Adopt the persona-prompt identity-declaration approach decided in
  SPEC-008 §5b.1: each Ghola's system prompt instructs the model to declare
  its peer identity on every Honcho-write call via a new `as_peer`
  parameter; the custom tool validates the declared identity against the
  allowlist before delegating to the Honcho SDK.
- Document and accept the "process-trusted → model-trusted" degradation
  explicitly. Defense-in-depth (Steward `product:` prefix enforced both in
  persona text AND in code) remains the safety net.
- Turn SPEC-008 acceptance criteria A4 and A5 from yellow to green at the
  production level — not just in the existing unit harness which sets the
  env directly.

## 2. Scope

In scope:

- New `as_peer` parameter on `honcho_remember` and `honcho_conclude` tool
  schemas in `.omp/tools/honcho/index.ts`. Validated against
  `CONCLUSION_WRITERS` for `honcho_conclude`. Steward `product:` prefix
  gate continues to fire on declared identity.
- Persona-text edits to all seven Gholas under `.omp/agents/{spec-writer,
  test-writer, implementer, validator, reviewer, steward, doc-scout}.md`
  adding the identity-declaration instruction in identity-natural language
  for each. Steward additionally retains the `product:` prefix instruction.
- An identity-spoofing-prevention mechanism per §3.1 (decision below):
  primary path is **option (c) — accept model-trust degradation, document
  it loudly, rely on persona prompts + Steward prefix + reviewer audit**.
  Fallback path if upstream ever exposes an in-process agent-name surface
  is **option (a)**, captured as a follow-up note rather than this slice's
  work.
- Extension of `.omp/test/honcho.test.ts` to cover the new `as_peer`
  parameter shape, allowlist enforcement, default-peer fallback for
  `honcho_remember`, and steward-prefix gate against the declared identity.
- One integration test under `.omp/test/migration/` that dispatches a
  validator persona via real `omp task` and asserts that the produced
  Honcho conclusion is attributed to `validator`, not to the parent's
  ambient `HONCHO_PEER_ID`.
- Updates to `.omp/tools/honcho/PORT-NOTES.md` documenting the identity
  model under the new `as_peer` contract and the explicit acceptance of
  model-trust.

Not in scope:

- Patching upstream `@oh-my-pi/pi-coding-agent` to expose an in-process
  per-agent identity field on `CustomToolContext`. Tracked as a follow-up
  in §5 Remaining; the primary-source check in §3.1 confirms it's not
  available in v14.4.0.
- Migrating any `.pi/` extension code; vanilla Pi remains untouched.
- Disabling Oh My Pi's autonomous memory feature (already covered by
  SPEC-008 §5.4).
- Reworking `honcho_recall` / `honcho_search` (read-side tools — identity
  spoofing on a query is not a security boundary).
- Per-Ghola model / thinkingLevel / fallback-chain configuration. Tracked
  as slice-008.3.

## 3. Implementation constraints

### 3.1 Identity-spoofing prevention — DECIDED: accept model-trust + document

Three primary-source checks, run against
`@oh-my-pi/pi-coding-agent@14.4.0` installed at
`/home/fr/.cache/.bun/install/global/node_modules/@oh-my-pi/pi-coding-agent`:

**(a) Read agent name from `ctx.sessionManager.getEntries()` — INFEASIBLE
in v14.4.0.** The `SessionEntry` union
(`src/session/session-manager.ts:206–220`) contains no agent-identity
entry type. The closest candidate, `SessionInitEntry`
(`src/session/session-manager.ts:162–173`), records
`{ systemPrompt, task, tools, outputSchema }` — agent **name** is not
included. The `AgentStartEvent` payload exposed to hooks
(`src/extensibility/hooks/types.ts:363–365`) is just
`{ type: "agent_start" }` with no agent identifier. Subagent dispatch in
`src/task/executor.ts:945–976` calls `createAgentSession` and embeds the
agent's `systemPrompt` text into the child session, but never writes the
agent's `name` into the child's `sessionManager`. Confirming this further:
the call to `session.sessionManager.appendSessionInit(...)` at
`src/task/executor.ts:1000–1005` passes `systemPrompt`, `task`, `tools`,
`outputSchema` only. To recover the persona name from inside the child
tool we would have to substring-match the system-prompt text against
known Ghola names — fragile (a future persona rename silently breaks
identity), and trivially confounded by any persona text that mentions
another Ghola by name.

**(b) Write active agent name to a session-scoped scratch file on
spawn — INFEASIBLE without a clean spawn seam, and racy if implemented.**
The hook surface fires `before_agent_start` (parent-side, before the
**parent** session loop) and `agent_start` (parent-side, no agent-name
payload). There is no `subagent_start` or `task_dispatch` hook event in
`src/extensibility/hooks/types.ts` (the union at `types.ts:535–537` lists
`AgentStartEvent` for the parent only). The event-bus emission inside
`runSubprocess` at `src/task/executor.ts:982–991` is on a private
`TASK_SUBAGENT_LIFECYCLE_CHANNEL`, not exposed via `HookAPI`. Even if we
wrote `<cwd>/.pi/.omp-active-agent.json` on every observed lifecycle
emit, the `task` tool runs subagents in parallel (see
`mapWithConcurrencyLimit` at `executor.ts:995`) and the file would race
between concurrent `validator` + `reviewer` dispatches, producing
incorrect attribution. Adding a per-task-id file is technically possible
but the custom-tool side has no way to learn the calling subagent's task
id — `CustomToolContext` (`src/extensibility/custom-tools/types.ts:67–82`)
does not expose `taskId`, `parentTaskPrefix`, or `agent`.

**(c) Accept model-trust degradation explicitly — DECIDED, primary path.**
Persona prompts instruct the model to declare its peer identity in the
call. The custom tool validates the **declared** identity against
`CONCLUSION_WRITERS` and applies the Steward `product:` prefix
invariant against the **declared** identity. A misbehaving model can
lie. This is the documented trade-off in SPEC-008 §5b.1 and is accepted.
Defense-in-depth holds for steward (the `product:` prefix doubles as a
content-shape audit trail visible to reviewer); for validator/reviewer,
audit-via-reviewer is the only line.

**Why we do not chase a partial mitigation.** A "scan
`ctx.sessionManager.getEntries()` for the most recent
`SessionInitEntry`'s `systemPrompt` text and substring-match
`/^name:\s*(\w+)$/m`" approach would technically work in the happy path,
but it adds:

- a load-bearing dependency on the persona-frontmatter format being
  embedded verbatim into the system prompt (today
  `executor.ts:958–965` wraps the agent system prompt inside
  `subagentSystemPromptTemplate` — the surrounding text could change in
  any minor upstream release, silently breaking the matcher);
- a fragile parser for content the upstream maintainer never promised
  to keep parseable;
- the false sense of security that the allowlist is "enforced" when in
  fact a model that lies about `as_peer` and matches the surrounding
  text shape will still succeed.

For the slice's stated trade-off (model-trust accepted, defense-in-depth
via Steward prefix), option (c) is honest and option-scanning is theatre.

**Follow-up trigger (not slice-008.1 work).** If upstream adds a
`subagent_start` hook event with an `agentName` payload, OR a field on
`CustomToolContext` like `ctx.activeAgent?.name`, OR an
`AgentStartEvent.agentName`, switch to that signal as a hard cross-check
against the declared `as_peer` and reject mismatches as `isError`.
File-tracked under "Remaining" in §5.

### 3.2 `as_peer` parameter shape — DECIDED

- **`honcho_conclude`**: `as_peer` is **REQUIRED**. No env-var fallback.
  Missing or empty `as_peer` returns `isError` with a message naming the
  expected parameter and the Gholas in `CONCLUSION_WRITERS`. Rationale:
  conclusions are durable peer-identity-bound writes; silently falling
  back to ambient env would re-create exactly the bug this slice exists
  to fix.
- **`honcho_remember`**: `as_peer` is **OPTIONAL**. If omitted, the tool
  falls back to the current behavior (`process.env.HONCHO_PEER_ID` →
  `hydrateFromConfigFile`). If supplied, the supplied value is used as
  the peer identity for the call. Rationale: `honcho_remember` is
  attribution-only, not a security boundary; existing behavior is
  preserved for non-Ghola callers and for legacy code paths during
  staged rollout.
- Validation order inside `honcho_conclude.execute`:
  1. Validate `as_peer` is present and non-empty. If not → `isError`.
  2. Validate `as_peer` ∈ `CONCLUSION_WRITERS` (use existing
     `isConclusionWriter` helper). If not → `isError` with the existing
     "peer X is not permitted to write conclusions" message, substituting
     the declared `as_peer` for the env-derived identity.
  3. If `as_peer === "steward"`, enforce the `product:` prefix
     invariant against `params.content`. (Existing branch at
     `index.ts:318–322` switches from `peerId === "steward"` to
     `params.as_peer === "steward"`.)
  4. Required-env check (`checkRequired`) — workspace/session/api-key.
  5. Network call. Pass `as_peer` to `client.peer(as_peer)` (replaces
     `client.peer(peerId)` at `index.ts:335`).
- TypeBox schema additions in the OMP factory at `index.ts:428–430`:
  - `ConcludeParams`: add `as_peer: Type.String({ minLength: 1,
    description: "The Ghola peer identity making this conclusion. MUST
    match the declaring agent's persona name. Required; the allowlist
    rejects calls without it." })`
  - `RememberParams`: add `as_peer: Type.Optional(Type.String({
    minLength: 1, description: "Optional override of the peer identity
    used to attribute this message. Defaults to the calling session's
    HONCHO_PEER_ID env." }))`

### 3.3 Persona-text changes — DECIDED

Each of `.omp/agents/{spec-writer, test-writer, implementer, validator,
reviewer, steward, doc-scout}.md` gets a new line under "Memory protocol"
or equivalent. Identity-natural phrasing per Ghola; semantically all say
the same three things:

1. "Your peer identity is `<name>`."
2. "When calling `honcho_remember`, pass `as_peer: '<name>'`."
3. "When calling `honcho_conclude`, pass `as_peer: '<name>'`. (Required.
   Calls without `as_peer` are rejected.)"

Gholas not in `CONCLUSION_WRITERS` (`spec-writer`, `test-writer`,
`implementer`, `doc-scout`) additionally get: "You are NOT permitted to
call `honcho_conclude`. If you attempt to, the call will be rejected."

`steward.md` retains: "Your conclusions MUST start with `product:` —
this is a dialect separator; engineering conclusions do not use it."

`validator.md` and `reviewer.md` get no special prefix instruction —
their conclusions are engineering-dialect by default.

Persona body order is preserved; the new instruction lives inside the
existing "Memory protocol" section so it's in the same lexical block as
the recall/remember/conclude rules already there.

### 3.4 Test migration — DECIDED: extend existing suite

Extend `.omp/test/honcho.test.ts` rather than create a parallel file.
Rationale: every existing test sets up `getEnv()` with a peer identity;
adding `as_peer` parameter coverage in the same `describe` blocks keeps
the env-vs-`as_peer` precedence rules colocated and discoverable. New
tests added (numbering matches §4 acceptance):

- `[unit] honcho_conclude as_peer parameter`:
  - rejects when `as_peer` is missing/empty
  - rejects when `as_peer` is `seshat` (orchestrator) even if env
    `HONCHO_PEER_ID=validator` (proves declared identity beats env)
  - accepts when `as_peer` is `validator`/`reviewer`/`steward`
  - rejects when `as_peer === "steward"` and content lacks `product:`
    prefix
  - accepts when `as_peer === "steward"` and content has `product:`
    prefix
- `[unit] honcho_remember as_peer parameter`:
  - omitting `as_peer` falls back to env-derived peer (existing
    behavior)
  - supplied `as_peer` is used as the peer identity for the call

Integration test added under `.omp/test/migration/identity.test.ts`
(new file under the migration suite that already houses A1–A10 specs):

- gated behind `OMP_LIVE_TESTS=1`
- dispatches a no-op validator task via `omp task`
- inspects the resulting Honcho conclusion list (using
  `listConclusionsForTest` from `.omp/tools/honcho/index.ts:378`) and
  asserts that the produced conclusion is attributed to `validator`,
  not to the parent orchestrator

### 3.5 Trade-off and security posture — DOCUMENTED

The slice ships a **model-trusted** allowlist. A misbehaving Ghola can
lie about `as_peer` and bypass the gate. The reasons we accept this:

1. The threat model for pi-seshat is not adversarial — Gholas are our
   own personas, dispatched by our own orchestrator. The allowlist
   exists to catch persona-prompt drift and accidental misuse, not
   adversarial model behavior.
2. Steward's `product:` prefix is an independent, content-shape
   invariant. Even if a non-steward Ghola lies about `as_peer ===
   "steward"`, the prefix on the resulting Honcho conclusion is a
   reviewer-visible audit trail of the lie.
3. Process-trusted enforcement requires a per-spawn env or per-agent
   context surface that v14.4.0 does not expose (§3.1). Building either
   ourselves means patching upstream — out of scope per SPEC-008 §5.2
   bus-factor decision.
4. `~/.omp/agent/.fallback-log.jsonl` and the `.honcho-state.json`
   counter together provide enough telemetry that a misbehaving Ghola
   would be detectable in post-hoc audit.

A comment block at the top of `.omp/tools/honcho/index.ts` (the
existing "Identity model" docstring at `index.ts:17–24`) is updated to
state the model-trust posture and reference this spec by id.

### 3.6 Backwards compatibility

- Vanilla `.pi/extensions/honcho/index.ts` is **not modified**. Pi
  invocations continue to use process-trusted env identity per SPEC-001.
- Skill `bin/` scripts that import the vanilla extension also unchanged
  (slice-008.2 governs those).
- The four-tools surface (`honcho_recall`, `honcho_search`,
  `honcho_remember`, `honcho_conclude`) keeps the same names. Only
  `honcho_remember` and `honcho_conclude` schemas grow a new field.
  Existing callers that don't pass `as_peer` still work for
  `honcho_remember` and start failing fast for `honcho_conclude`
  (intentional — the failure is the slice's correctness contract).

## 4. Acceptance criteria

Each criterion is binary PASS/FAIL. All must pass before archive.

1. **Tool-schema change — `honcho_conclude.as_peer` required.** TypeBox
   schema for `honcho_conclude` declares `as_peer: Type.String({
   minLength: 1 })`. A call with `as_peer` omitted or empty string
   returns `isError: true` with a message naming the missing parameter.
   (Unit, extends `[unit] honcho_conclude peer-allowlist gate`.)
2. **Tool-schema change — `honcho_remember.as_peer` optional.** TypeBox
   schema for `honcho_remember` declares
   `as_peer: Type.Optional(Type.String({ minLength: 1 }))`. A call with
   `as_peer` omitted falls back to env-derived peer; a call with
   `as_peer="X"` uses `X` as the peer for the network call. (Unit, two
   cases.)
3. **Allowlist enforcement on `as_peer`, not env.** With `getEnv()`
   returning `HONCHO_PEER_ID="validator"` and `as_peer="seshat"`,
   `honcho_conclude` returns `isError: true`. With env
   `HONCHO_PEER_ID="seshat"` and `as_peer="validator"`,
   `honcho_conclude` does NOT return `isError` at the pre-network gate.
   (Unit.)
4. **Steward prefix gate against declared identity.** With
   `as_peer="steward"` and content `"some conclusion"`, returns
   `isError`. With `as_peer="steward"` and content
   `"product: some conclusion"`, does NOT return `isError` at the
   pre-network gate. With `as_peer="validator"` and content `"some
   conclusion"` (no prefix), does NOT return `isError`. (Unit, three
   cases.)
5. **Persona-text correctness — all seven Gholas.** Each of the seven
   `.omp/agents/*.md` files contains an identity-declaration
   instruction line that names the Ghola's own persona name and
   instructs declaration via `as_peer`. The four non-conclusion-writer
   Gholas (`spec-writer`, `test-writer`, `implementer`, `doc-scout`)
   additionally state that they are NOT permitted to call
   `honcho_conclude`. `steward.md` retains the `product:` prefix
   instruction. (File-content assertion, scriptable; tests live under
   `.omp/test/migration/persona-identity.test.ts` or inline in the
   identity test file.)
6. **Identity-spoofing-prevention posture documented.** The header
   docstring of `.omp/tools/honcho/index.ts` and
   `.omp/tools/honcho/PORT-NOTES.md` both contain language explicitly
   stating that the allowlist is model-trusted, name SPEC-008.1 as the
   governing decision, and reference the §3.1 (a)/(b)/(c) trade-off.
   (File-content assertion.)
7. **Integration test under real `omp task` dispatch.** A test that
   spawns the `validator` Ghola via `omp task` (or the equivalent
   in-process subagent harness) and confirms that the recorded
   conclusion's peer attribution is `validator`, regardless of the
   parent process's `HONCHO_PEER_ID`. Gated behind `OMP_LIVE_TESTS=1`;
   skips loudly if env unset. (Integration; new file under
   `.omp/test/migration/`.)
8. **SPEC-008 A4 turns green at production level.** The allowlist
   behaviors A4 specifies — orchestrator (`seshat`) rejected, validator
   accepted, steward `product:` prefix enforced — pass against the new
   `as_peer` contract under live `omp` dispatch (not just unit
   harness). (Manual, scripted; status line in `MIGRATION.md` flips
   from yellow to green as part of slice-archive.)
9. **SPEC-008 A5 turns green for trailers + identity.** All seven
   personas dispatch under `omp` and the orchestrating session's
   trailer block records the correct `Peer` trailer per dispatch.
   (Manual, scripted; uses `.omp/hooks/specsafe-subagents.ts` trailer
   output as the test surface.)
10. **No regression on existing tests.** Existing `.omp/test/honcho.test.ts`
    suite passes unchanged where its semantics are preserved
    (`isConclusionWriter`, `sanitizeErrorForDisplay`, env-missing tests,
    workspace-scope rejection). Tests that change semantics under the
    `as_peer` contract (the allowlist + steward-prefix gate tests) are
    updated in-place to use `as_peer` explicitly. (Existing 197/8/0
    baseline preserved or improved.)
11. **Lint + typecheck.** `bun run typecheck` and `bun run test`
    (including new tests) both pass. Pre-commit secret scanner clean.
    (CI / manual.)

## 5. Open questions / risks

### Resolved (decisions made in this spec; do not re-litigate during implementation)

- **§3.1 — Identity-spoofing prevention.** Option (c) — accept
  model-trust, document explicitly. Options (a) and (b) rejected on
  primary-source evidence; see §3.1 for citations.
- **§3.2 — `as_peer` shape.** Required for `honcho_conclude`, optional
  with env fallback for `honcho_remember`. No fallback for `conclude`.
- **§3.3 — Persona-text wording.** Each Ghola gets identity-natural
  phrasing of the three-point instruction (name, remember, conclude).
  Non-writers additionally get the explicit "you cannot call conclude"
  line.
- **§3.4 — Test layout.** Extend `.omp/test/honcho.test.ts`; add one
  integration test file under `.omp/test/migration/identity.test.ts`.
- **§3.5 — Trade-off posture.** Model-trust accepted, defense-in-depth
  via Steward prefix and reviewer audit.
- **`as_peer` vs `peer` vs `peer_id`.** Use `as_peer`. Matches the
  HANDOFF document's wording, reads naturally in persona text ("call
  honcho_conclude as_peer 'validator'"), and avoids collision with the
  Honcho SDK's own `peerId` / `peer` field names which appear in
  `HonchoToolRuntimeEnv`.

### Remaining for implementer to surface during execution

- **Upstream-evolution trigger.** If between spec-approval and
  implementation, upstream `@oh-my-pi/pi-coding-agent` ships a
  `subagent_start` hook event with an `agentName` payload, OR adds an
  agent-identity field to `CustomToolContext`, OR adds an
  `agentName` field to `AgentStartEvent`, the implementer should
  surface this and we re-evaluate §3.1 before writing the
  identity-validation code. The cross-check would be a hard reject of
  any `as_peer` that disagrees with the in-process signal. Do NOT
  silently add this without surfacing — it changes the security
  contract from model-trusted to process-trusted, which is a posture
  change Luci should explicitly approve.
- **Persona text drift.** If the seven personas' `.omp/agents/*.md`
  files have been edited between spec-approval and implementation in
  ways that conflict with the §3.3 phrasing, surface the diff before
  applying. Do not silently overwrite recent persona changes.
- **Skill `bin/` interaction.** Slice-008.2 will refactor skill `bin/`
  scripts to shell out to a CLI. If any skill currently issues
  `honcho_conclude` calls, they will start failing fast under this
  slice. Surface any such call sites during implementation; the fix
  is to add `as_peer` to those call sites OR defer them to slice-008.2
  (preferred — skills shouldn't conclude).

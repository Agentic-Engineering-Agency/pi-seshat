## What's underused or broken

- **Zero live runtime exposure.** Per your Q1: nothing in this repo —
  not one of the six skills, not one of the seven personas — has been
  exercised on a real workload. Every "✅ Pass" in MIGRATION.md is a
  unit-test or pin-test pass, not a behavioral one. The system is
  spec-correct and observation-empty.
- **Slice lifecycle has no programmatic entry point under `omp`.**
  Vanilla Pi shipped three tools (`specsafe_begin/_end/_status`) that
  wrote `.pi/.honcho-state.json`. The omp port consciously did NOT
  reimplement them — `.omp/hooks/specsafe-session.ts` only *reads* the
  state file (lines 117-156) and `PORT-NOTES.md:17-22` documents the
  drop. Net effect: under `omp` dispatch, `state.currentSlice` is
  always `null` unless you drop back into `pi` to open a slice, which
  means the auto-commit-with-trailers hook returns early at line 133
  of `specsafe-subagents.ts` and the entire trailer machinery silently
  no-ops. This is the load-bearing gap.
- **Four personas ship a contract they can't execute.** `spec-writer`,
  `reviewer`, `steward`, and `doc-scout` all instruct the model to
  "invoke `/skill:latest-docs show <lib>`", but their `tools:`
  frontmatter omits `bash` (the actual entry point for skill bins is
  `bun run .omp/skills/.../bin/*.ts`). Examples:
  `.omp/agents/doc-scout.md:4` (tools list) vs lines 19-21 (skill
  invocation). Either the personas need `bash`, or omp needs a
  first-class `skill` tool, or the bodies need rewording to dispatch
  through an agent that has bash.
- **README.md identity model is stale post-008.6.** Lines 45-63
  describe workspace=`one per project`, peer=`seshat` (orchestrator) +
  one per Ghola, and a per-spawn child-env-injection flow that
  `PORT-NOTES.md:44-55` explicitly says was NOT ported. AGENTS.md
  (slice-008.6) and your own opening prompt confirm the current wiring
  is workspace=`oh-my-pi`, session=`luci-<basename-of-cwd>`, no
  `seshat` peer. README.md and AGENTS.md disagree. CLAUDE.md:43 also
  still references `.pi/extensions/honcho/index.ts` for the
  `product:` enforcement when the active code under `omp` is
  `.omp/tools/honcho/index.ts:343-347`.
- **Three drills deferred on a system about to be dogfooded.** A3
  (fallback-chain integration test), A7 (`--i-approve` gate
  integration test), A9 (rollback drill round-trip) are all 🟡 in
  MIGRATION.md:60-66. Per your Q1+Q5, dogfooding will surface these
  faster than synthetic tests, but A9 specifically depends on you
  not painting yourself into an unrecoverable corner — the rollback
  hatch is unverified.
- **`registry.json` is 11/11 unverified URLs.** Every entry carries
  `"verified": false` and `_meta.note` says they were not live-checked
  at seed time. doc-scout's first real call could hit a 404 on any of
  them.

## Proposed enhancements (ranked by impact-per-effort)

### 1. Slice lifecycle entry point under `omp` — S/M, blocks dogfooding

Without a way to open a slice under `omp`, every Ghola dispatch you do
in a real project will commit work *without* `Spec-Slice:` trailers —
defeating the SpecSafe audit story. Three viable shapes, in ascending
effort: (a) a thin `.omp/skills/specsafe/bin/specsafe.sh` CLI you run
from a terminal alongside `omp` to open/close slices (writes the same
state file, no in-process integration needed); (b) restore the three
tools as an `.omp/tools/specsafe/` `CustomToolFactory` mirroring the
honcho-tool pattern; (c) keep slice management in vanilla `pi` and
dual-run. (a) is the cleanest first move — markdown + bash, no test-
writer step, ~30 LOC. Prerequisite: none. Acceptance: under `omp`,
running the skill opens a slice, dispatching a Ghola produces a commit
with all four trailers, closing the slice writes a history entry.

### 2. Persona bash-or-rewrite repair — S, markdown-only

For `spec-writer`, `reviewer`, `steward`, `doc-scout`: pick one
resolution and apply consistently. My recommendation is to **add
`bash` to those four personas with a constrained instruction**
("`bash` is permitted only to invoke `bun run .omp/skills/*/bin/*.ts`
— any other use is a persona breach"), because rewriting four
personas to dispatch through a fifth is more surface for less safety.
Prerequisite: none. Acceptance: every persona that references
`/skill:` in its body has `bash` in its `tools:` frontmatter, and the
constrained instruction is present.

### 3. `coherence` skill — M, your Q4 elevation

Read-only cross-source consistency checker, no `--i-approve` gate
needed (it doesn't mutate). Subcommands: `coherence check
linear-vs-specs` (Linear issues with no matching `specs/<KEY>__*.md`
slice; specs with no matching Linear ticket), `coherence check
trailers-vs-linear` (recent commit `Spec-Slice:` trailers whose key
isn't in Linear, or whose Linear state doesn't match what the trailer
implies), `coherence check brief-coverage` (Linear tickets in
`in_progress`/`in_review` with no `specs/briefs/*.md`). Output is
plain text, exit 0 if clean, exit 1 if drift detected. Prerequisite:
`linear` skill operational (so live `LINEAR_API_KEY` confirmed first).
Acceptance: skill detects three planted drift cases on a sandbox
workspace.

### 4. `env-doctor` skill — S, first thing to run in every dogfood session

Single-shot verifier: `HONCHO_API_KEY` round-trip via a no-op
`session.search`, `LINEAR_API_KEY` round-trip via a `viewer` query,
`gh auth status`, `omp` install + login (`omp config get`), the four
`~/.omp/agent/{hooks,tools,agents,skills}` symlinks resolve into
`$PWD/.omp/`, and `.pi/.honcho-state.json` integrity (parses, has the
required keys, mode 0600). One command, one report. Prerequisite:
none. Acceptance: passes cleanly on this repo today; produces a
specific failure line for each thing you can break by-hand.

### 5. README.md + CLAUDE.md identity-model rewrite — S, markdown-only

Bring README.md:45-63 in line with the slice-008.6 wiring (workspace
`oh-my-pi`, session `luci-<basename>`, no `seshat` peer, no per-spawn
child env injection — point to PORT-NOTES.md for the truth). Update
CLAUDE.md:43 path reference from `.pi/extensions/honcho/index.ts` to
`.omp/tools/honcho/index.ts`. Prerequisite: none. Acceptance: a fresh
reader of README.md alone reaches the same identity model as a fresh
reader of AGENTS.md alone.

### 6. `registry.json` URL probe + smoke fetch — S, config-only

Script that runs `latest-docs fetch <lib>` (no `--refresh` first, then
`--refresh`) for each of the 11 entries; on success flips
`verified: true`; on failure logs the status code. Run once, manually,
before doc-scout's first real dispatch. Prerequisite: none.
Acceptance: 11/11 entries either flipped to `verified: true` or have
a documented exclusion reason.

## What to explicitly NOT do

- **No MCP-server replacements for any of the six skills.** Pi's
  README and your own working preferences argue CLI-first; MCP servers
  bypass the `--i-approve` gate idiom and make audit-log capture
  asymmetric.
- **No pre-apply-without-approval paths.** Every external mutation
  stays dry-run-by-default with `--i-approve` required to execute. Do
  not "promote" a dry-run to real on the basis of a previous run, do
  not add an `OMP_AUTOAPPROVE` env var, do not let a Ghola pass
  `--i-approve` itself.
- **No CostCounter token-accumulation under `omp`.** `PORT-NOTES.md:23-28`
  explicitly preserves the source's no-mutation stance; the original
  session extension never accumulated tokens either. Fabricating an
  accumulator inside the omp port would be a plausible-lie addition,
  precisely the failure mode the porting rules forbid.
